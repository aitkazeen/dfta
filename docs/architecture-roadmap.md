# Financer — архитектура и план работ

**Продукт:** мобильный финансовый помощник (React Native). **Ядро:** анализ графиков валют \+ анализ новостного фона → прогноз по паре → push-уведомление. **Активы MVP:** USD, EUR, RUB, KZT (базовые пары USD/KZT, USD/RUB, EUR/USD, EUR/KZT, RUB/KZT) \+ расширяемый список. **Бэкенд:** Node.js / Fastify \+ Prisma \+ TypeScript. **Вне скоупа:** iOS-виджет (WidgetKit), торговля и брокерские операции, рекомендации по акциям/облигациям.

## 0\. Ключевые продуктовые решения (и почему)

| Вопрос | Решение | Обоснование |
| :---- | :---- | :---- |
| Как строить прогноз | **Гибрид: детерминированные тех-индикаторы \+ сентимент новостей \+ LLM-объяснение.** ML-модель — вторым этапом | Фиатные пары с фиксируемыми/управляемыми курсами (RUB, KZT) плохо предсказываются чистым ML на малой выборке. Правила дают предсказуемость, LLM — читаемое объяснение, а слой абстракции `ForecastEngine` позволяет заменить движок на ML без переписывания приложения |
| Что показываем пользователю | **Направление \+ вероятность \+ горизонт \+ 3 причины.** Не «купи/продай» | Юридически и по правилам App Store безопаснее. См. §8 |
| Частота прогноза | 1 раз в сутки (утро) \+ внеплановый при «событии» (резкое движение / важная новость) | Экономит квоты API и не спамит пользователя |
| Канал доставки | **Push-уведомления** — единственный «внешний» канал | Виджет убран из скоупа, вся ценность вне приложения идёт через push. Значит качество, тайминг и формулировки уведомлений — критичная фича, а не второстепенная |
| Платформа | **iOS \+ Android одновременно** | Без виджета исчезает единственная причина делать iOS-first |

### 0.1 Что изменилось после отказа от виджета

Решение убрать WidgetKit — не просто минус одна фича. Оно снимает три ограничения сразу:

- **Не нужен prebuild / CNG.** Остаёмся в managed-workflow Expo: не требуется Xcode 16, macOS 15 и экспериментальный плагин `@bacons/apple-targets`. Уходит самый непредсказуемый по срокам блок, и разработку можно вести не только с Mac.  
- **Android почти бесплатен.** Нативной iOS-специфики не остаётся, кроссплатформа получается из коробки — запускаться можно сразу на обе платформы вместо «iOS сейчас, Android потом».  
- **Срок MVP сокращается примерно на 2 недели** и, что важнее, снижается дисперсия оценки.

Обратная сторона: пропадает пассивное присутствие на домашнем экране. Компенсируется двумя вещами — качественными push-уведомлениями и (по желанию) Live Activities позже. Ретеншен теперь целиком держится на уведомлениях, поэтому этап 5 становится ключевым, а не вспомогательным.

### Почему модули, а не микросервисы

Шесть «сервисов» на схеме — это шесть папок в одном Fastify-приложении, а не шесть развёрнутых процессов. Границы между ними держатся дисциплиной импортов: модуль общается с соседом только через явно экспортированный интерфейс, а не лезет в его внутренности. Если позже понадобится разнести их по процессам — границы уже проведены, и это будет вопрос деплоя, а не переписывания.

Отдельным процессом с самого начала выносится только **worker**: фоновые задачи не должны конкурировать с HTTP-запросами за event loop, и падение воркера не должно ронять API.

### Принцип отказоустойчивости источников

Каждый внешний источник — за интерфейсом (`IQuoteProvider`, `INewsProvider`). Реализации: primary \+ 1–2 fallback, переключение через circuit breaker. Ни один слой приложения не знает, откуда пришли данные.

Без DI-контейнера это делается фабрикой: функция читает конфиг и возвращает нужную реализацию, всё остальное приложение работает с интерфейсом. Явно и без магии.

**Про NestJS.** Роадмап изначально предполагал Nest ради DI-контейнера и готовой модульной структуры. Решено остаться на Fastify: скелет работает, а Nest добавляет заметный слой абстракций для того, кто первый раз пишет бэкенд. Паттерн «интерфейс \+ подменяемая реализация» реализуется фабричной функцией на два десятка строк. Вернуться к вопросу имеет смысл, когда ручная сборка зависимостей начнёт мешать — не раньше. Nest, к слову, умеет работать поверх Fastify, так что миграция не означает смены HTTP-слоя.

## 3\. Источники данных

### 3.1 Котировки (FX)

Нужны: спот-курс \+ дневные и часовые исторические свечи по фиатным парам, включая **KZT и RUB** — их поддерживают не все провайдеры, это фильтр номер один при выборе.

**Стратегия:** один платный primary \+ бесплатный fallback \+ официальные ЦБ как «источник истины» для отображаемого пользователю официального курса.

| Роль | Кандидаты | Что проверить перед выбором |
| :---- | :---- | :---- |
| Primary (intraday) | ForexRateAPI, UniRateAPI, exchangeratesapi.io, Twelve Data | Есть ли KZT; минимальный интервал (1h vs 1d); глубина истории; лимит запросов; SLA |
| Fallback | Frankfurter (ECB, бесплатный, без ключа) | Только дневные данные и валюты ЕЦБ — KZT нет, годится только для EUR/USD |
| Официальные курсы | **API ЦБ РФ** (`cbr.ru/scripts/XML_daily.asp`), **НБ РК** (`nationalbank.kz/rss/rates_all.xml`) | Бесплатно, официально, 1 раз в сутки |

**Обязательный шаг до старта разработки:** прогнать каждый провайдер тестовым запросом на USD/KZT и RUB/KZT за 2 года и сверить исторические значения с ЦБ. Расхождения на экзотических парах — норма, и это влияет на всю модель.

### 3.2 Новости

| Провайдер | Плюсы | Минусы |
| :---- | :---- | :---- |
| **Marketaux** | Готовый sentiment score −1…1, теги сущностей (в т.ч. forex), 5000+ источников | Бесплатный тариф \~100 запросов/сутки |
| Alpha Vantage News & Sentiment | Есть бесплатный доступ, встроенный сентимент | Фокус на US-акциях, слабое покрытие СНГ |
| APITube / EODHD / Finnhub | Широкое покрытие | Платно |
| **RSS ЦБ РФ, НБ РК, Минфин, Interfax, KASE** | Локальный контекст, критичный для RUB/KZT | Парсить самим, нет сентимента |

**Решение:** Marketaux как основной поставщик глобального фона \+ собственный RSS-коллектор локальных источников, сентимент для которых считаем сами (см. §5.2).

Investing.com и TradingView как источники **не рассматриваются**: у Investing.com нет публичного API принципиально (запрет от их собственных поставщиков данных), а T\&C прямо запрещают копирование и использование их рыночной информации для создания сервисов. TradingView отдаёт только веб\-виджеты-iframe, непригодные для RN.

### 3.3 Макро-календарь

Ставки ЦБ, инфляция, заседания — критично для FX. Источники: Trading Economics API (платно) либо ручной seed-справочник дат заседаний ЦБ РФ / НБ РК / ФРС / ЕЦБ на год вперёд. Для MVP достаточно ручного справочника.

**Почему TimescaleDB:** hypertables \+ continuous aggregates закрывают агрегацию свечей и retention без отдельной тайм-серийной БД. Одна Postgres на всё — меньше инфраструктуры на старте.

**`forecast_outcome` — не опциональна.** Без неё вы не сможете ни показать пользователю реальную точность, ни оценить, стал ли новый движок лучше старого. Пишется автоматически по расписанию, когда истекает горизонт прогноза.

## 5\. Прогнозный пайплайн

### 5.1 Технический слой (детерминированный)

Считается на каждой свече, кэшируется в `indicator_value`:

- **Тренд:** EMA20/50/200, наклон, положение цены относительно EMA  
- **Импульс:** RSI(14), MACD(12,26,9), Stochastic  
- **Волатильность:** ATR(14), ширина полос Боллинджера  
- **Уровни:** локальные экстремумы за 30/90 дней, круглые уровни

Выход: `technicalScore ∈ [−1, +1]` — взвешенная сумма нормализованных сигналов. Веса вынесены в конфиг, не в код.

### 5.2 Новостной слой

RSS/API → дедуп по URL-хэшу и по эмбеддингу заголовка (одна новость в 10 изданиях)

        → фильтр релевантности (сущности: валюта, страна, ЦБ, нефть, санкции, ставка)

        → сентимент: score от Marketaux, где есть;

          для локальных RSS — LLM-классификация батчем (дёшево на Haiku-класс модели)

        → impact\_score: источник × свежесть × релевантность паре

        → newsScore ∈ \[−1, \+1\] — взвешенное среднее за окно 24ч с экспоненциальным затуханием

### 5.3 Слияние и объяснение

interface ForecastEngine {

  predict(input: ForecastInput): Promise\<ForecastResult\>;

  readonly version: string;

}

// v1: RulesForecastEngine — technicalScore \* 0.6 \+ newsScore \* 0.4, калибровка по истории

// v2: MlForecastEngine    — LightGBM/XGBoost, вызывается по HTTP из отдельного Python-сервиса

LLM вызывается **только для генерации текста объяснения** по уже посчитанным числам — не для расчёта самого прогноза. Это делает результат воспроизводимым, дешёвым и проверяемым.

Промпт получает: значения индикаторов, топ-5 новостей, итоговый скор — и возвращает 2–3 предложения \+ три коротких драйвера для карточки прогноза и пуша.

**Стоимость:** \~20 пар × 1 вызов в сутки \= \~600 вызовов в месяц, порядка $2–3/мес на модели уровня Haiku. Цифра не растёт с числом пользователей — прогноз общий и кэшируется по хэшу входа.

### 5.4 Калибровка

Confidence нельзя брать «из головы». Правильный путь: прогнать движок на исторических данных (walk-forward, минимум 2 года), построить таблицу «скор → фактическая частота попадания», и confidence брать из неё. Иначе пользователь увидит «уверенность 85%» при реальной точности 52%.

## 7\. Уведомления — центральная фича

Без виджета push остаётся единственным способом дотянуться до пользователя вне приложения. Поэтому здесь нельзя ограничиться «отправляем и ладно».

| Тип | Триггер | Пример |
| :---- | :---- | :---- |
| Ежедневный прогноз | Cron, утро в TZ пользователя | «USD/KZT: вероятен рост к 512–515 ₸ (уверенность 68%)» |
| Пороговое | Курс пересёк заданное значение | «USD/KZT пробил 510 ₸» |
| Резкое движение | |Δ| \> 2×ATR за час | «RUB/KZT: аномальное движение −1.8% за час» |
| Важная новость | impact\_score \> порога | «НБ РК повысил базовую ставку» |

**Обязательные механики:**

- Тихие часы и доставка в утреннее окно по таймзоне пользователя  
- Дедупликация: не более N уведомлений в сутки на пару, подавление повторов об одном событии  
- Группировка через thread-id (iOS) / channel \+ группы (Android)  
- Rich push: краткий текст прогноза прямо в уведомлении, чтобы ценность считывалась без открытия приложения  
- Deep links в нужный экран  
- `notification_log` \+ метрика open rate по типам — иначе невозможно понять, какие уведомления полезны, а какие раздражают

**Настройки пользователя обязательны с первого релиза.** Единственный канал коммуникации, который нельзя выключить по типам, быстро приводит к отключению уведомлений целиком — а это потеря пользователя.

## 8\. Юридические ограничения и App Store

Это не формальность — на этом заворачивают релизы.

- **Никаких инвестиционных рекомендаций.** Формулировки — «вероятное направление», «аналитический сигнал», а не «покупайте». Никаких кнопок исполнения сделок и связи с брокером — иначе включается требование Apple о подаче приложения лицензированной финансовой организацией.  
- **Никаких индивидуальных рекомендаций по инструментам** (акции, облигации, портфель). В РФ это деятельность по инвестиционному консультированию: только через членство в СРО и единый реестр инвестсоветников ЦБ. В РК — лицензия и квалификационные требования АРРФР к сотруднику. Обезличенная аналитика по рынку под это не подпадает — персональная подпадает.  
- **Дисклеймер** на онбординге и на экране прогноза: информационный характер, не инвестиционная рекомендация, прошлые результаты не гарантируют будущих.  
- **Раскрытие использования ИИ.** По правилам 2026 года нужно явно объяснять, что часть контента генерируется автоматически, и получать согласие на передачу данных третьим сторонам (в т.ч. AI-сервисам).  
- **Честная точность.** Показывайте реальную статистику из `forecast_outcome`, а не маркетинговое число. Это одновременно и защита, и главный аргумент доверия.  
- **Privacy Manifest** (`PrivacyInfo.xcprivacy`) \+ Data Safety для Google Play; лицензии провайдеров данных — проверить условия отображения и хранения котировок.

## 9\. План работ

Оценки — для команды из 1 сильного fullstack \+ 1 RN разработчика. Соло — умножайте на \~1.7. Соло и первый бэкенд — умножайте на 2,5–3 и не считайте это провалом: часть времени уйдёт на изучение, а не на код.

### Этап 0\. Подготовка (1 неделя)

- Прогнать 3–4 FX-провайдера на реальных парах с KZT/RUB, сравнить с ЦБ, выбрать primary \+ fallback  
- Зарегистрировать ключи: FX, Marketaux, LLM, Apple Developer Program, Google Play Console  
- Собрать датасет: 2+ года дневных свечей по 5 парам \+ архив новостей — понадобится для калибровки  
- Определить точный список пар и валют MVP

**Выход:** решение по провайдерам, ключи, датасет в CSV/Parquet.

### Этап 1\. Фундамент (2 недели)

Частично сделано: скелет `mobile/` \+ `server/`, Docker Compose с Postgres, роут `/health`, цепочка бэкенд ↔ база прогнана вживую.

Осталось:

- Добавить в Compose Redis; включить расширение TimescaleDB в существующей Postgres  
- Схема БД (§4), переход с `prisma db push` на `prisma migrate dev`, hypertables и continuous aggregates  
- `IQuoteProvider` \+ 2 реализации \+ фабрика выбора по конфигу \+ circuit breaker  
- Второй контейнер `worker` на BullMQ: крон сбора котировок  
- Удалить модель `Ping` и одноимённый роут  
- Expo Router, базовая навигация, дизайн-система  
- CI: линт, тесты, EAS Build (internal distribution) для обеих платформ

**Выход:** котировки идут в БД по расписанию; приложение собирается и ставится на устройства iOS и Android.

### Этап 2\. Данные и графики (2 недели)

- Расчёт индикаторов, эндпоинты candles/indicators/quote/snapshot, WS-стрим  
- Экран пары: свечной график (Skia), таймфреймы, зум, кросс-хэйр  
- Главный экран, watchlist, поиск, offline-кэш через TanStack Query \+ MMKV  
- Авторизация (Apple/Google), JWT, refresh

**Выход:** рабочее приложение-графики. Уже показываемо.

### Этап 3\. Новости и сентимент (2 недели)

- `INewsProvider`, интеграция Marketaux, RSS-коллектор ЦБ РФ / НБ РК / KASE  
- Дедупликация (URL-хэш \+ эмбеддинги заголовков), привязка новостей к парам  
- LLM-классификация сентимента батчем для локальных источников, кэш результатов  
- Лента новостей с фильтром по паре и меткой тональности

**Выход:** newsScore считается и хранится по каждой паре.

### Этап 4\. Прогнозный движок (2–3 недели)

- Интерфейс `ForecastEngine`, реализация `RulesForecastEngine`  
- **Бэктест на историческом датасете, walk-forward, подбор весов**  
- **Калибровка confidence по таблице попаданий** — без этого этап не считается закрытым  
- LLM-генерация объяснения и трёх драйверов, кэш по хэшу входа  
- Cron генерации прогнозов, запись `forecast` \+ отложенная запись `forecast_outcome`  
- Экран прогноза: направление, диапазон, уверенность, драйверы, история точности

**Выход:** честный прогноз с измеримой точностью.

### Этап 5\. Уведомления (2 недели) — ключевой этап

- APNs/FCM, регистрация токенов, notification-service  
- Правила алертов (порог, прогноз, движение, новость), UI настройки по типам  
- Тихие часы, дедуп, лимиты частоты, `notification_log`  
- Rich push с текстом прогноза, группировка, deep links  
- Метрики доставки и open rate по типам уведомлений

**Выход:** пользователь получает ценность, не открывая приложение.

### Этап 6\. Полировка и релиз (2 недели)

- Онбординг, дисклеймеры, экран раскрытия ИИ, политика конфиденциальности  
- Privacy Manifest, Play Data Safety, метаданные сторов, скриншоты, TestFlight \+ Internal Testing  
- Sentry, PostHog, алерты на падение провайдеров  
- Нагрузочное тестирование, лимиты API, ретраи  
- Подача в App Review и Google Play Review

**Итого MVP: \~12–13 недель** (≈3 месяца) для двоих, сразу на две платформы.

### После MVP

- ML-движок (`MlForecastEngine`, Python-сервис за HTTP), A/B против правил  
- **Виджеты** (iOS WidgetKit \+ Android Material You), если push-метрики покажут спрос на пассивное присутствие  
- Live Activities при резких движениях  
- Подписка (RevenueCat): больше пар, больше алертов, горизонт 7 дней  
- Портфельный трекер: пользователь вносит активы сам, приложение считает доходность и распределение (без рекомендаций — юридически безопасно)  
- Расширение на крипту и металлы — архитектура источников уже готова

## 10\. Риски и что с ними делать

| Риск | Вероятность | Митигация |
| :---- | :---- | :---- |
| Нет качественных intraday-данных по KZT/RUB | **Высокая** | Проверить на этапе 0 до написания кода. Fallback — работать на дневных свечах и официальных курсах ЦБ |
| Точность прогноза окажется около случайной | **Высокая** | Не продавать точность как фичу. Ценность — агрегация \+ объяснение \+ уведомления. Показывать честную статистику из `forecast_outcome` |
| Пользователь отключает push → теряется весь внешний канал | **Высокая** (выросла после отказа от виджета) | Настройки по типам, жёсткие лимиты частоты, отслеживать open rate и отключения как ключевую метрику |
| Отказ App Review / Google Play (финансовое приложение) | Средняя | §8 выполнить до подачи, а не после отказа |
| Расходы на LLM растут с числом пользователей | Низкая | LLM только для текста объяснения, один вызов на пару в сутки, кэш по хэшу входа |
| Провайдер данных упал / поднял цены | Средняя | Интерфейсы \+ circuit breaker с первого дня; никогда не звать провайдера напрямую из бизнес-логики |
