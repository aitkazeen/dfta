# Разбор проекта: что где лежит и как это работает

Подробный гайд к скелету. `README.md` — короткая шпаргалка на каждый день,
этот файл — объяснение, почему всё устроено именно так.

---

## 1. Общая картина

Три отдельные вещи, которые общаются по сети:

```
┌──────────────────────┐
│  Expo-приложение     │   живёт на телефоне
│  React Native        │   Docker к нему отношения не имеет
└──────────┬───────────┘
           │  HTTP-запросы: GET http://192.168.x.x:3000/ping
           ▼
┌──────────────────────┐
│  api                 │   контейнер, порт 3000
│  Node + Fastify      │   принимает запросы, отвечает JSON
└──────────┬───────────┘
           │  SQL через Prisma: postgres://app:secret@db:5432/app
           ▼
┌──────────────────────┐
│  db                  │   контейнер, порт 5432
│  Postgres 16         │   хранит данные
└──────────────────────┘

     api и db поднимает docker compose одной командой
```

Ключевая мысль: **Docker нужен для серверной части**. Мобильное приложение
собирается и запускается напрямую на твоей машине — в контейнер его класть
незачем и технически нельзя.

## 4. Разворачивание, шаг за шагом

### Шаг 0. Подготовка

В папке `server/` может лежать `node_modules` — я его создавал при проверке
кода. Удали его перед началом, чтобы не путался:

```bash
rm -rf server/node_modules server/package-lock.json
```

Не критично, но чище. Внутрь Docker-образа он всё равно не попадёт —
это отсекает `.dockerignore`.

### Шаг 1. Поднять бэкенд

Из корня проекта:

```bash
docker compose up --build
```

Что произойдёт по шагам:

1. Docker качает образы `node:22-slim` и `postgres:16-alpine` (первый раз
   ~2 минуты, дальше из кеша)
2. Собирает образ для `api` по `server/Dockerfile`
3. Запускает `db`, ждёт пока healthcheck скажет «Postgres готов»
4. Запускает `api`, тот выполняет `prisma db push` — создаёт таблицы
5. Стартует Fastify

Готово, когда в логах:

```
api-1  | {"level":30,"msg":"Server listening at http://0.0.0.0:3000"}
```

Проверка из браузера — <http://localhost:3000/health>. Должно вернуться:

```json
{"ok":true,"time":"2026-07-26T..."}
```

Если открылось — серверная часть работает. Терминал не закрывай, там логи.

### Шаг 2. Запустить приложение

В **новом** терминале:

```bash
cd mobile
npm install
npx expo start
```

Появится QR-код. Дальше:

- **iPhone** — сканируй камерой, откроется в Expo Go
- **Android** — открой Expo Go и сканируй оттуда

Телефон и компьютер должны быть в одной Wi-Fi сети.

### Шаг 3. Проверить связку

В приложении под заголовком написан адрес, на который оно будет ходить.
Жми кнопку «Дёрнуть /ping». Ожидаемо:

```
pong
запись в БД #1
до неё было: 0
```

Жмёшь ещё раз — счётчик растёт. Это значит, что цепочка
телефон → api → Postgres работает целиком, и данные реально пишутся в базу.

## 5. Разбор файлов

### `compose.yaml` — что поднимать

Главный файл. Описывает два сервиса.

```yaml
services:
  api:
    build: ./server        # собрать образ из папки server по её Dockerfile
    ports:
      - "3000:3000"        # ЛЕВОЕ:ПРАВОЕ = порт_на_твоей_машине:порт_в_контейнере
```

Про `ports` стоит понять точно: контейнер по умолчанию закрыт наглухо.
Строка `"3000:3000"` пробивает дырку — обращение на `localhost:3000`
с твоей машины перенаправляется внутрь контейнера на порт 3000.
Если 3000 у тебя занят, меняешь **левое** число: `"3001:3000"`.

```yaml
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app
```

Хост здесь `db` — это имя сервиса из этого же файла. Compose поднимает
внутреннюю сеть, где контейнеры видят друг друга по именам, как по DNS.
`localhost` написать нельзя: для контейнера `api` localhost — это он сам.

```yaml
    depends_on:
      db:
        condition: service_healthy
```

Без `condition` Docker ждёт только *старта* контейнера с базой. Но Postgres
после старта ещё несколько секунд инициализируется и соединения не принимает —
api успевает подключиться, получить отказ и упасть. `service_healthy`
заставляет ждать реальной готовности.

```yaml
  db:
    image: postgres:16-alpine     # готовый образ, свой Dockerfile не нужен
    ports:
      - "5432:5432"               # чтобы подключаться с хоста через DBeaver
    volumes:
      - pgdata:/var/lib/postgresql/data
```

`volumes` — самое важное для базы. Файловая система контейнера умирает
вместе с ним. Именованный том `pgdata` живёт отдельно, поэтому
`docker compose down` + `up` не стирает данные. Стирает только `down -v`.

```yaml
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      retries: 10
```

Каждые 5 секунд внутри контейнера выполняется `pg_isready`. Когда команда
вернёт успех — сервис помечается healthy, и api получает зелёный свет.

### `compose.override.yaml` — надстройка для разработки

Compose автоматически подхватывает файл с таким именем и **накладывает**
его поверх `compose.yaml`. Так боевая конфигурация остаётся чистой:
на сервере этого файла просто не будет.

```yaml
    build:
      target: build       # остановиться на первой стадии Dockerfile
```

Первая стадия содержит `tsx`, `typescript` и остальные dev-зависимости.
Финальный образ их не содержит — а для разработки они нужны.

```yaml
    command: sh -c "npx prisma db push && npm run dev"
```

Переопределяет `CMD` из Dockerfile: сначала синхронизировать таблицы
со схемой, потом запустить watch-режим.

```yaml
    volumes:
      - ./server/src:/app/src
      - ./server/prisma:/app/prisma
      - /app/node_modules
```

Первые две строки монтируют твои папки внутрь контейнера. Правишь файл
в редакторе — он мгновенно меняется и внутри, `tsx watch` видит и
перезапускает сервер. Пересборка образа не нужна.

Третья строка выглядит странно — путь без источника. Это «анонимный том»,
и он решает конкретную проблему. Пакеты внутри контейнера собраны под Linux;
если твой хостовый `node_modules` (собранный под macOS или Windows)
примонтируется поверх, нативные модули сломаются. Анонимный том прикрывает
эту папку и оставляет контейнерную версию.

### `server/Dockerfile` — как собрать образ

Двухстадийная сборка. Смысл: инструменты сборки в финальный образ не нужны.

```dockerfile
FROM node:22-slim AS build          # стадия 1: здесь компилируем
...
FROM node:22-slim                   # стадия 2: сюда кладём только результат
COPY --from=build /app/dist ./dist
```

Из первой стадии во вторую переезжает только собранный `dist/`. TypeScript,
tsx, исходники — остаются в первой и в финальный образ не попадают. Образ
получается заметно меньше.

Второй приём — порядок копирования:

```dockerfile
COPY package*.json ./     # сначала только манифесты
RUN npm install
COPY . .                  # и только потом весь код
```

Docker кеширует каждый слой. Если `package.json` не менялся, слой с
`npm install` берётся из кеша, и пересборка после правки кода занимает
секунды вместо минут. Скопируй код раньше — и кеш будет сбрасываться
на каждое изменение любого файла.

### `server/.dockerignore`

```
node_modules
dist
.git
.env
```

Работает как `.gitignore`, но для сборки образа. Без него `COPY . .`
затащит внутрь твой локальный `node_modules` — образ распухнет, а нативные
модули будут собраны под не ту систему. Файл маленький, но пропускать его
нельзя. `.env` в списке потому, что секреты в образе не хранят.

### `server/src/main.ts` — сам сервер

```ts
const app = Fastify({ logger: true })

app.get('/health', async () => ({ ok: true }))
```

Роут — это «когда придёт GET на такой путь, выполни эту функцию и отдай
то, что она вернула». Fastify сам превращает объект в JSON и ставит
заголовки. Свои эндпоинты добавляй рядом.

```ts
app.listen({ port, host: '0.0.0.0' })
```

`host: '0.0.0.0'` внутри Docker обязателен. По умолчанию Node слушает
`127.0.0.1` — только петлевой интерфейс внутри контейнера. Проброс портов
при этом не работает, снаружи ничего не видно, и ошибка выглядит загадочно:
контейнер жив, логи чистые, но всё «Connection refused».

### `server/prisma/schema.prisma` — описание БД

```prisma
model Ping {
  id        Int      @id @default(autoincrement())
  createdAt DateTime @default(now())
}
```

Из этого описания Prisma делает две вещи: создаёт таблицу в Postgres
и генерирует типизированный клиент. После генерации в коде появляется
`db.ping` с автодополнением полей — опечатка не скомпилируется.

Модель `Ping` — заглушка для демонстрации. Удаляй и описывай своё.

### `mobile/src/api.ts` — адрес бэкенда

Самое частое место, где всё ломается у новичков, поэтому оно вынесено
в отдельный файл и вычисляется автоматически.

Проблема: `localhost` на телефоне означает сам телефон, а не твой компьютер.

| Где запускаешь | Правильный адрес хоста |
|---|---|
| Реальный телефон | IP компьютера в Wi-Fi, напр. `192.168.1.15` |
| Android-эмулятор | `10.0.2.2` — специальный алиас |
| iOS-симулятор | `localhost` работает, он делит сеть с macOS |

Код берёт `Constants.expoConfig.hostUri` — Expo знает, с какого IP отдаёт
бандл телефону (что-то вроде `192.168.1.15:8081`), — вытаскивает оттуда
хост и подставляет порт 3000. Руками ничего прописывать не надо.

### `mobile/App.tsx` — экран

Обычный React, но вместо `<div>` и `<p>` — `<View>` и `<Text>`, а вместо
CSS — объект стилей через `StyleSheet.create`. Три состояния: `loading`,
`result`, `error`. По нажатию дёргается `/ping`, результат рисуется
карточкой. Отправная точка для твоих экранов.

## 6. Путь одного запроса

Полезно один раз проследить целиком:

1. Палец жмёт кнопку в Expo Go на телефоне
2. `fetch('http://192.168.1.15:3000/ping')` уходит в Wi-Fi
3. Пакет приходит на твой компьютер, на порт 3000
4. Docker видит правило `"3000:3000"` и переправляет в контейнер `api`
5. Fastify находит роут `/ping`, вызывает обработчик
6. Prisma формирует SQL и шлёт его на `db:5432` по внутренней сети Compose
7. Postgres выполняет, пишет строку в том `pgdata`, возвращает результат
8. Fastify сериализует ответ в JSON
9. Тот же путь обратно, `setResult` перерисовывает экран

Когда что-то не работает — определи, на каком из девяти шагов обрывается.
`/health` в браузере проверяет шаги 3–5, кнопка в приложении — все девять.

## 7. Ежедневная работа

```bash
docker compose up              # поднять
docker compose up --build      # поднять с пересборкой
docker compose logs -f api     # логи бэкенда, -f = следить
docker compose exec api sh     # шелл внутри контейнера
docker compose ps              # что сейчас запущено
docker compose down            # остановить
docker compose down -v         # остановить и стереть базу
```

**Когда нужна пересборка `--build`:** поменялся `package.json`, `Dockerfile`
или `compose.yaml`. Правки в `src/**` подхватываются сами.

**Поменял схему БД** — накати изменения:

```bash
docker compose exec api npx prisma db push
```

**Посмотреть данные глазами:**

```bash
docker compose exec api npx prisma studio
```

Либо подключись любым GUI на `localhost:5432` — юзер `app`, пароль `secret`,
база `app`.

## 8. Типичные ошибки

**`Network request failed` в приложении.**
Смотри, какой адрес показан в приложении под заголовком, и открой его
в браузере **телефона**. Не открылось — либо телефон в другой сети
(частая причина: гостевой Wi-Fi или мобильный интернет), либо файрвол
компьютера режет входящие на порт 3000.

**`port is already allocated`.**
Порт занят. Найди кто: `lsof -i :3000` (macOS/Linux). Или поменяй левое
число в `ports`.

**api перезапускается по кругу, в логах `ECONNREFUSED db:5432`.**
Проверь `DATABASE_URL` — хост должен быть `db`. И что `depends_on`
с `condition: service_healthy` на месте.

**Поменял зависимости, а их не видно.**
`docker compose up --build`. Без этого используется старый образ.

**`Cannot find module '@prisma/client'`.**
Клиент не сгенерирован: `docker compose exec api npx prisma generate`.

**Всё сломалось, разбираться некогда.**
Полный сброс, база при этом теряется:

```bash
docker compose down -v
docker compose up --build
```

## 9. Git

Отдельная от Docker вещь, но начать стоит сразу:

```bash
git init
git add .
git commit -m "скелет проекта"
```

`.gitignore` уже настроен — `node_modules`, `dist`, `.env` в репозиторий
не уедут.

Про секреты: сейчас пароль `secret` лежит прямо в `compose.yaml`. Для
локальной песочницы это нормально — база доступна только с твоей машины.
Перед выкладкой куда-либо пароли выносят в `.env`, который в git не
коммитится, а в репозитории оставляют `.env.example` с пустыми значениями.

## 10. Куда двигаться

1. **Свои модели.** Замени `Ping` в `schema.prisma` на реальные сущности,
   прогони `prisma db push`
2. **Свои роуты.** Пиши в `server/src/`. Когда роутов станет больше пяти —
   разнеси по файлам и подключай через плагины Fastify
3. **Миграции вместо `db push`.** Когда схема устаканится, переходи на
   `prisma migrate dev`: он сохраняет изменения в файлы, которые едут
   в git и накатываются на проде предсказуемо
4. **Навигация в приложении** — `expo-router`, экраны раскладываются
   по файлам как в Next.js
5. **Запросы по-взрослому** — `@tanstack/react-query`: кеш, повторы,
   состояния загрузки без ручного `useState`
6. **Ещё сервисы.** Нужен воркер на Python или сервис на C#? Это ещё один
   блок в `compose.yaml` со своим Dockerfile. Обращение — по имени сервиса,
   `http://worker:8000`. Смешивать языки в одном compose — обычная практика
